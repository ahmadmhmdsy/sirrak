1. This SDK has **no cmdline-tools and no avdmanager** (only emulator + platform-tools + one system

## 2. The problem in one paragraph

The emulator's **virtual data partition is 6 GB and 4.9 GB is free**, the AVD lives on **C:** where
only ~45 GB is free, and the AVD plus its snapshot already eat ~20 GB. A 2B Q4 model is ~1.4 GB, so
one model fits — barely — but a second model, an embedding model (~300 MB), the app, chat databases
and documents do not. Worse, the AVD has **4 GB RAM**, and Android itself plus a 2B Q4 model can
easily exceed that, so the model-load test may be killed by the OS — which would produce a false
negative about our own engine.

The emulator is **not** short of CPU or user patience (it boots fine), it is short of **virtual
disk, RAM and host disk headroom** — all three are fixable without buying anything.

## 3. What the emulator can and cannot tell us about Nawa

| Question | Emulator answer | Verdict |
|---|---|---|
| Does the UI render, RTL work, Compose screens navigate? | Yes (Google Play image, API 36) | **Use emulator** |
| Do chat streaming, Room, download manager, RAG parsing work? | Yes, functionally | **Use emulator** |
| Does the model load or crash? | Yes, but only x86_64 builds; memory is the emulator's, not the phone's | **Use emulator with limits** |
| How fast is decode/prefill/TTFT on a real phone? | **No** — x86_64 host CPU, no big.LITTLE, no thermal throttling, no phone memory bandwidth | **Physical device required (H1)** |
| Does NPU/LiteRT acceleration work? | **No** — no Qualcomm/MediaTek/Tensor NPU in the emulator | **Physical device required (H2)** |
| Is the Arabic voice actually pleasant? | Audio input/output exists, but it is the host's audio stack; intelligibility still needs humans | **Physical device + listeners (H3)** |
| Battery/thermal behaviour? | Meaningless | **Physical device** |
| Play Store install / policy flow / default-assistant behaviour? | Partially (Play Store image exists; assistant role may be testable) | **Emulator + one real device** |
| PocketPal baseline feature comparison | Possible by sideloading its 295 MB GitHub APK (if its ABIs include x86_64) | **Try; not critical** |

**Consequence for the plan:** the emulator shortcuts UI/E2E work while the phone is being bought;
it does not replace the physical test phone required by Step Zero H1/H2/H3.

### 3.1 ABI consequence for the build

The AVD is **x86_64**; the release target is **arm64-v8a**. To run on the emulator, the debug build
must also produce an **x86_64** llama.cpp/whisper build, i.e. the dev flavour builds ABIs
x86_64 + arm64-v8a while the release flavour stays arm64-only. This was anticipated in the
architecture ADR-11; it is now a concrete task, not a note. Emulator speed numbers must never be
reported as phone performance.

## 6. Exact steps (PowerShell, Windows)

> Safety: copy before delete; verify paths; do not run the delete lines until the copy boots.
> Ask before deleting anything. Commands written for PowerShell 7.

**Step 1 — stop emulator and prepare**

    $sdk = "$env:LOCALAPPDATA/Android/Sdk"
    $adb = "$sdk/platform-tools/adb.exe"
    & $adb emu kill

**Step 2 — delete the stale test AVD (frees 6.86 GB on C:)**

    Remove-Item "$env:USERPROFILE/.android/avd/test_avd.avd" -Recurse -Force
    Remove-Item "$env:USERPROFILE/.android/avd/test_avd.ini" -Force

**Step 3 — move AVD home to D:**

    New-Item -ItemType Directory -Force D:/Android/avd | Out-Null
    Copy-Item "$env:USERPROFILE/.android/avd/Small_Phone.ini" D:/Android/avd/
    Copy-Item "$env:USERPROFILE/.android/avd/Small_Phone.avd" D:/Android/avd/ -Recurse
    # edit D:/Android/avd/Small_Phone.ini: set path=D:/Android/avd/Small_Phone.avd
    setx ANDROID_AVD_HOME "D:/Android/avd"
    $env:ANDROID_AVD_HOME = "D:/Android/avd"

**Step 4 — create Nawa_Phone (recommended device geometry)**

    $avdmanager = "$sdk/cmdline-tools/latest/bin/avdmanager.bat"
    & $avdmanager create avd -n Nawa_Phone -k "system-images;android-36.1;google_apis_playstore;x86_64" -d pixel_5 --sdcard 8000M
    # then edit D:/Android/avd/Nawa_Phone.avd/config.ini and set:
    #   disk.dataPartition.size=16G
    #   sdcard.size=8000M
    #   hw.ramSize=6144
    #   vm.heapSize=2048
    #   hw.cpu.ncore=6
    #   fastboot.forceFastBoot=no
    #   fastboot.forceColdBoot=yes

**Step 5 — wipe once so the new sizes take effect, then boot**

    & "$sdk/emulator/emulator.exe" -avd Nawa_Phone -wipe-data -no-snapshot -no-boot-anim -gpu auto

**Step 6 — verify inside the guest**

    & $adb devices
    & $adb shell df -h /data /sdcard
    & $adb shell "cat /proc/meminfo | head -3; nproc"

**Step 7 — headless mode for CI/E2E (no window, deterministic)**

    & "$sdk/emulator/emulator.exe" -avd Nawa_Phone -no-window -no-audio -no-boot-anim -no-snapshot -gpu swiftshader_indirect

**Step 8 — push a model to a debuggable app for tests**

    & $adb push D:/models/qwen3.5-2b-q4_k_m.gguf /data/local/tmp/model.gguf
    & $adb shell run-as app.sirrak.spike cp /data/local/tmp/model.gguf files/model.gguf

(For release testing use the in-app downloader and SAF picker instead; run-as only works on
debuggable builds. Play Store system images are not rootable — do not try qemu-img resize or
resize2fs on them; the supported path is config.ini + wipe, as above.)

## 8. What still requires the physical phone

1. **H1 speed:** decode/prefill/TTFT on Snapdragon 7-series or better — including a **grounded 250–330-token prompt** (H3c measured 35–43 s prefill on the x86_64 emulator, shape-only; doc 10 §3.8), because RAG answers make prefill the launch-critical number.
2. **H2 NPU:** LiteRT-LM acceleration on a real SoC; emulator has no NPU.
3. **H3 voice quality:** recording with a real microphone and listening tests.
4. **Thermals/battery:** sustained inference behaviour.
5. **Assistant role and OEM behaviour:** not fully testable on stock Google Play image.

So: emulator for velocity, phone for truth. The used-phone purchase stays in the Step Zero budget.
