# 04 — Accessibility, RTL, Arabic typography & localization audit (Sirrak 1.1.0 / versionCode 14)

**Area owner:** a11y-i18n-auditor · **Task:** task-4 · **Date:** 2026-11-25
**Method:** static reading of the UI modules (app/, core/design, feature/*), the live accessibility tree produced by journey-runner's uiautomator dumps (build/ux-audit/logs/*-nodes.txt), screenshots (build/ux-audit/shots/), and a WCAG contrast computation over all 5 theme packs × light/dark using the app's own Contrast.ratio formula and the hexes in ThemePacks.kt. No app source was modified; no build or emulator was run by this auditor.
**Findings schema:** AREA-NN with AREA in {A11Y, RTL, I18N, FS}. Ratios are WCAG 2.x normal-text thresholds unless marked "UI" (3:1).

## Executive summary (5 lines)

1. **Biggest strengths:** device-verified RTL mirroring is essentially correct (auto-mirrored back/send/history icons, RTL nav order, bidi-wrapped meter numbers, supportsRtl), AR/EN key parity is perfect (651/651, no orphans, no missing keys), and the theme-contrast gate is a real data-driven test.
2. **Biggest risk:** the app is effectively unusable with a screen reader at the core surfaces — there is no live region anywhere (streaming answers, dictation failures, download/copy confirmations are silent), and every icon-only button and clickable row exposes its label on a separate, non-clickable accessibility node (device tree proves it).
3. Second risk: the contrast gate only checks 20 pairs, so text the app really paints (e.g. onSurfaceVariant on surfaceContainerHigh) is ungated and **the default pack fails AA at 4.39:1**; several painted UI boundaries are 1.0–1.4:1.
4. Third risk: text scaling is multiplicative (in-app 130% x system 200% = 260%, no cap) while text boxes are fixed-height/single-line; the model chip already clips its own state to a dot at 100%.
5. **Counts:** P0 = 0 · **P1 = 7** · **P2 = 13** · **P3 = 13** (total 33). No P0: nothing here blocks an unimpaired user's task; all P1s break assistive-tech users' core paths, which the brief treats as blocking for those users.

## Findings

### A11Y-01 — Streaming answers are never announced (no live region in the whole app)
- **Severity:** P1   **Confidence:** high   **Effort:** S
- **Where:** chat answer while streaming (core/design/src/main/java/app/sirrak/core/design/Chat.kt:168-190 AssistantProse, :443-449 StreamingLabel; feature/chat/src/main/java/app/sirrak/feature/chat/ChatScreen.kt:283-288)
- **What happens now:** a search of all main-source Kotlin finds **zero** liveRegion / LiveRegionMode usages; the only status-ish semantics in the app are heading() (Markdown.kt:553), two stateDescription/contentDescription blocks in ModelControls.kt (103-106, 213) and one custom onClick in DictationControls.kt (134-145). The streaming answer text and the streaming label are plain Text nodes, so TalkBack announces nothing while tokens arrive and nothing when the answer completes.
- **Why it hurts:** a blind user starts a generation, hears nothing for several seconds, cannot tell whether the model is working, and must re-focus the transcript repeatedly to discover whether anything arrived. The app's single core promise — a local assistant that answers — is silent for screen-reader users.
- **Fix:** wrap AssistantProse (while streaming) in Modifier.semantics { liveRegion = LiveRegionMode.Polite } and put a short state description on the item ("جارٍ التوليد…" then "اكتملت الإجابة"); on completion announce once via a polite region rather than on every token.
- **Verify:** TalkBack on: start a generation from the empty chat; the region must speak the first words and completion without touching the screen. Add a UI test asserting the item node's LiveRegion semantics property is set while streaming.

### A11Y-02 — Every icon-only button's name sits on a separate, non-clickable node
- **Severity:** P1   **Confidence:** high   **Effort:** M
- **Where:** global back, history, new chat, copy, regenerate, report, attach, send (core/design/.../Page.kt:43-48; core/design/.../Chat.kt:234-254; feature/chat/.../ChatScreen.kt:209-218, 449; device tree build/ux-audit/logs/12-history.xml, 10-chat-empty.xml)
- **What happens now:** the uiautomator tree shows, for example, the back button as a clickable/focusable node with **empty text and empty content-desc** at [16,150][112,246] (48 dp) and, as its child, a non-clickable View carrying content-desc="رجوع" at [40,174][88,222] (24 dp). The same split exists for history (فتح قائمة المحادثات), new chat, copy (نسخ الإجابة), regenerate, report and attach. The pattern is structural: the description is set on the Icon child while IconButton/clickable owns the action on the parent.
- **Why it hurts:** a screen-reader user swipes onto an unnamed 48 dp target ("double-tap to activate" with no name), then onto a named 24 dp blurb that does nothing. None of the app's navigation or answer actions is announced as "name, button" — WCAG 4.1.2 (A) fail on the primary controls.
- **Fix:** put the name on the actionable node: IconButton(onClick=…, modifier = Modifier.semantics { contentDescription = label; role = Role.Button }) (the dictation mic in DictationControls.kt:126-145 already does exactly this correctly and is announced as class Button in the same dump), or pass Modifier.clickable(role = Role.Button, onClickLabel = label) plus a merged descendant. Remove the duplicate description from the child Icon.
- **Verify:** uiautomator dump again: each 48 dp clickable node must carry its own content-desc and class=…Button; TalkBack must read "رجوع، زر".

### A11Y-03 — Clickable rows/cards are not merged, so the row itself has no name
- **Severity:** P1   **Confidence:** high   **Effort:** M
- **Where:** history row (feature/chat/.../ChatHistory.kt:248-253), settings rows (core/design/.../Settings.kt:67-78), suggestion cards (core/design/.../Chat.kt:363-366), model chip (Chat.kt:398-407), licence rows (app/.../AboutLicences.kt:112-116), HF rows (feature/models/.../HfBrowseScreens.kt:211-213, 746-748), installed-model rows (feature/models/.../ModelManagerSection.kt:368), attachment source rows (feature/chat/.../AttachmentUi.kt:471-478), document rows (feature/chat/.../RagUi.kt:304-310).
- **What happens now:** Modifier.clickable publishes the click action but does not merge descendants, and only one row type in the app compensates (ModelControls.kt:123-124 adds .semantics(mergeDescendants = true) {}). Device evidence: the history row is a clickable View [24,396][696,555] with **no text/desc**, and its title, preview and "2 رسالة" are three separate TextViews inside it (12-history-nodes.txt lines 5-8). The chat header chip is one clickable View [232,164][575,260] with two text children (10-chat-empty-nodes.txt lines 3-4).
- **Why it hurts:** TalkBack reads the row as an unnamed button and then the label as a separate dead stop; the user cannot tell which conversation/card/row they are about to open, and selection gestures do not map to the visible target.
- **Fix:** add .semantics(mergeDescendants = true) {} to the row containers before .clickable (or build the rows with a merging surface), keeping the same visible layout. Prefer selectable for single-choice rows (it merges by contract) — the app's own switch/toggle rows show the pattern.
- **Verify:** the row must appear in uiautomator dump as one clickable node whose text contains title+preview+count; TalkBack must read the whole row in one stop.

### A11Y-04 — The composer and the history search box have no accessible name (placeholder only)
- **Severity:** P1   **Confidence:** high   **Effort:** S
- **Where:** chat composer (core/design/.../Chat.kt:109-136, placeholder composited inside decorationBox), conversation search (feature/chat/.../ChatHistory.kt:136-152)
- **What happens now:** both fields expose a BasicTextField/EditText node with no label/content-desc; the placeholder is a child Text node. Device tree (10-chat-empty.xml): the message field is android.widget.EditText [252,890][564,986] with no text/desc and a child TextView "اسأل عن أي شيء…". In the history search dump the field is likewise an EditText with an empty hint and a child placeholder.
- **Why it hurts:** a screen-reader user lands on an "edit box" with no name — they cannot tell whether it is the message composer or the search field, and the name disappears the moment anything is typed (WCAG 3.3.2/4.1.2, A).
- **Fix:** give each field a real label: add Modifier.semantics { contentDescription = <label> } (or a visible label = {} on the Material field) using the existing strings ("اسأل عن أي شيء" is a placeholder, not a label — add strings.xml labels such as "رسالتك" / "ابحث في المحادثات").
- **Verify:** TalkBack must read "رسالتك، حقل إدخال" when the field is empty and while typing; same for search.

### A11Y-05 — Dictation state strips are silent, including failures and the recording timer
- **Severity:** P1   **Confidence:** high   **Effort:** S
- **Where:** voice recording/transcribing/failure strips (feature/voice/src/main/java/app/sirrak/feature/voice/DictationControls.kt:197-223, 226-282, 284-312, 315-347)
- **What happens now:** when recording starts, transcribing starts or dictation fails, a strip is inserted above the composer with Surface/Text only — no liveRegion, no announceForAccessibility, no state description on the mic. The failure strip (errorContainer + reason + dismiss) appears silently.
- **Why it hurts:** a blind user taps the mic, cannot tell whether recording actually started, cannot hear the failure reason when it fails, and does not know that transcription ended and text was inserted. The mic description does flip start/stop, but the reason/state never reaches the user.
- **Fix:** make each strip a polite live region keyed on its state (Modifier.semantics { liveRegion = LiveRegionMode.Polite } on the Surface), and give the mic stateDescription ("يسجّل" / "يفرّغ" / "خامل"). Do not announce the per-second timer; announce start, stop, and result.
- **Verify:** TalkBack on, tap mic (TOGGLE and HOLD modes), speak, stop: "جارٍ التفريغ" and the inserted-text result must be spoken; force a failure (no model) and the reason must be spoken without navigating.

### A11Y-06 — Default pack fails AA on text it actually paints (4.39:1) — gate never checks that pair
- **Severity:** P1   **Confidence:** high   **Effort:** S
- **Where:** onSurfaceVariant on surfaceContainerHigh: status pill NEUTRAL (core/design/.../Page.kt:97), active conversation row (feature/chat/.../ChatHistory.kt:247 background; :279-283 preview text; :286-290 "2 رسالة"); also the transcribing strip (DictationControls.kt:213-214).
- **What happens now:** measured over the palette hexes with WCAG maths: GirihInk (default) light **onSurfaceVariant on surfaceContainerHigh = 4.39:1** (needs 4.5:1 for 12–14 sp text); on surfaceContainerHighest it is **4.03:1**. Screenshot build/ux-audit/shots/12-history-ar.png shows the active row: the title reads clearly while the preview and the message count are visibly washed out on the tonal row. ThemePacks.contrastPairs() (ThemePacks.kt:114-138) gates onSurfaceVariant/surfaceContainer but not …/surfaceContainerHigh.
- **Why it hurts:** the active conversation, its preview and its message count are the only state feedback in the history list; at 4.39:1 low-vision users lose the preview and count exactly on the row they selected — the one row where context matters most.
- **Fix:** either darken surfaceContainerHigh/Highest in the default (and other) packs until onSurfaceVariant reaches 4.5:1, or paint the preview/count with onSurface on high containers; add the pair to contrastPairs so the existing test enforces it.
- **Verify:** ThemePacksTest.everyGatedPairMeetsWcagInEveryPackAndMode must include the new pair and pass for all 5 packs × 2 modes; re-shoot the history screen and measure the rendered pair.

### A11Y-07 — Contrast gate covers only 20 of the pairs the app paints; several ungated pairs fail
- **Severity:** P2   **Confidence:** high   **Effort:** M
- **Where:** core/design/src/main/java/app/sirrak/core/design/ThemePacks.kt:108-138 (gate) vs the paint sites below; core/design/src/test/.../ThemePacksTest.kt iterates only that list
- **What happens now:** the doc comment says the list is "the pairs the app actually paints", but measured values show painted-but-ungated pairs including: outline/surfaceContainerLow **2.82:1** (GirihInk light) and outline/background **2.95:1** — used as control boundaries; outlineVariant/surfaceContainerLow **1.33:1** (segmented-button inactive border, Settings.kt:153); hairline dividers **1.03–1.41:1** across packs (Settings.kt:118, card borders Chat.kt:92, RagUi.kt:98/140/374); onSurfaceVariant/surfaceContainerHighest **4.03:1**; secondary/surfaceContainerHigh **4.46:1**. The claimed "tightest 5.73:1 body" holds only for the 20 gated pairs, not for all painted text.
- **Why it hurts:** the gate reads as a guarantee and reviewers trust it; in practice the default pack paints secondary metadata and control outlines below threshold. Low-vision users get faint separators and faint metadata, and regressions cannot be caught by the existing test.
- **Fix:** extend contrastPairs to every painted fg/bg combination (include surfaceContainerHigh/Highest, inverseSurface/inverseOnSurface, error and tertiary on surface, outline and outlineVariant where used as boundaries, and separately the disabled composites as informational), then either fix the palettes or move those elements to a passing role.
- **Verify:** print/assert the full matrix in the test; the default pack must report no sub-4.5 body pair and no sub-3.0 boundary pair.

### A11Y-08 — Segmented-button boundaries are about 1.3:1 — unselected options lose their visible extent
- **Severity:** P2   **Confidence:** medium   **Effort:** S
- **Where:** settings choice row (core/design/.../Settings.kt:141-163, inactiveBorderColor = outlineVariant at :153), library tabs (app/.../LibraryScreen.kt:195-200 inactive container = surfaceContainerLow), screenshot 00-baseline-settings-root-ar.png (النماذج/التنزيلات/الوسائط tabs)
- **What happens now:** an unselected option is drawn as a transparent container with a 1 dp outlineVariant border on the surfaceContainerLow card; measured GirihInk light outlineVariant/surfaceContainerLow = **1.33:1** (best pack 1.77:1). In the screenshot the unselected tabs are visible but extremely faint.
- **Why it hurts:** WCAG 1.4.11 wants 3:1 for the visual information that identifies a control; low-vision users see three labels floating with no tap extents and may mis-target adjacent options. The label text passes, so this is "hard to operate", not "unreadable".
- **Fix:** use outline (3:1 or better in most packs — and fix the packs where it is 2.82) or a tonal container (surfaceContainer/secondaryContainer at low emphasis) for the unselected segment instead of outlineVariant.
- **Verify:** measure the rendered border pixel against the card in the screenshot/tooling; add an outlineVariant-as-boundary entry to the contrast test at the UI tier.

### A11Y-09 — Copy confirmation is a silent icon swap that reverts after 1.8 s
- **Severity:** P2   **Confidence:** high   **Effort:** S
- **Where:** chat answer actions, copy button (core/design/.../Chat.kt:234-245 swaps ContentCopy to Check; ChatScreen.kt:304-308 sets copiedAnswerId, reset by the 1800 ms LaunchedEffect)
- **What happens now:** the only feedback is the glyph changing to a check with primary tint and a content-description change on a child icon node; no announcement, no visible text, no snackbar.
- **Why it hurts:** a screen-reader user presses "copy answer", hears nothing, and cannot know whether the clipboard now holds the answer; sighted users see a small glyph change for less than two seconds.
- **Fix:** announce on copy (polite live region on a status Text, or announceForAccessibility(copiedLabel) once) and keep the check state for the copied answer until another action; a snackbar "نُسخت الإجابة" is acceptable and testable.
- **Verify:** TalkBack: press copy and hear "نُسخت الإجابة" once; paste elsewhere to confirm the clipboard.

### A11Y-10 — Download progress and pause/resume changes never reach the screen reader
- **Severity:** P2   **Confidence:** high   **Effort:** S
- **Where:** models download row (feature/models/src/main/java/app/sirrak/feature/models/ModelManagerSection.kt:433-475; percent text :449-456, progress bar :444-447, pause/cancel :469-474)
- **What happens now:** LinearProgressIndicator exposes its range info, but the progress text (percent · downloaded/total) and phase changes (PAUSED to DOWNLOADING, retry) are plain Text with no live region; the pause button flips to resume with no announcement.
- **Why it hurts:** a blind user starting a 1 GB download cannot hear progress or completion and does not know whether pause worked; they must re-focus the row to poll.
- **Fix:** mark the phase text liveRegion = Polite keyed on phase (throttle percent announcements to about every 10%) and put a stateDescription on the row ("جارٍ التنزيل 34٪", "متوقف مؤقتًا").
- **Verify:** TalkBack: start a download and hear the state change; press pause and hear "متوقف مؤقتًا"; let one complete and hear completion.

### A11Y-11 — Screen, section and sheet titles are not headings

### A11Y-12 — Disabled send button: no reason, and the disabled control barely differs from its container
- **Severity:** P2   **Confidence:** high   **Effort:** S

### A11Y-13 — Document picker row exposes two competing targets (row + checkbox)
- **Severity:** P2   **Confidence:** high   **Effort:** S
- **Where:** chat document picker sheet (feature/chat/.../RagUi.kt:304-321: Row.clickable(enabled = selectable, onClick = onToggle) with no role, containing Checkbox(onCheckedChange = …))
- **What happens now:** the row is clickable (no role, no merge) and the Checkbox is a second toggleable node with its own role; both toggle the same state. Unready documents render a disabled row plus a disabled checkbox with only an alpha-faded label.
- **Why it hurts:** TalkBack presents two targets for one action with different announced roles/states; users toggle twice (off then on) or get contradictory announcements, and the disabled state has no spoken reason.
- **Fix:** make the row a single toggleable(role = Role.Checkbox, value = checked) with mergeDescendants = true, pass Checkbox(onCheckedChange = null), and add a stateDescription for the unready case.
- **Verify:** the dump must show one checkable node per document whose text includes the document name and status.

### A11Y-14 — Context-meter warning appears silently
- **Severity:** P2   **Confidence:** high   **Effort:** S
- **Where:** chat budget line (feature/chat/src/main/java/app/sirrak/feature/chat/ChatMeter.kt:33-37, 62-68)
- **What happens now:** meter_overflow / meter_near warnings are inserted as a second Text line without any live region; the user is told (visually) that the oldest turns will be dropped, but only if they look.
- **Why it hurts:** a screen-reader user's conversation is silently truncated — the first they know is that context "disappeared"; this is a status message under WCAG 4.1.3.

### A11Y-15 — Citation chips: about 32 dp tap area, no role, no merged label
- **Severity:** P2   **Confidence:** high   **Effort:** S
- **Where:** chat citations under a grounded answer (feature/chat/.../RagUi.kt:370-397: .clickable at :379, padding :380, two Texts :383-395)
- **What happens now:** the chip height is labelMedium line (16 sp) plus 12 dp vertical padding, about 28–32 dp; the clickable Row has no role and no merge, so its name is the child texts and its extent is below the 48 dp platform minimum (it still passes WCAG 2.5.8 AA's 24 dp minimum, so this is a platform-guideline and motor-access issue, not an AA fail).
- **Why it hurts:** small targets are hard for users with tremor; a screen reader announces an unnamed control and does not convey the role (WCAG 4.1.2, A).
- **Fix:** Modifier.heightIn(min = 48.dp).clickable(role = Role.Button).semantics(mergeDescendants = true) {} plus onClickLabel = "افتح المقتطف".
- **Verify:** the dump shows one clickable node 48 dp or taller whose text is the document name and page.

### A11Y-16 — Remove-document icon button and its chip are 40 dp
- **Severity:** P3   **Confidence:** high   **Effort:** S
- **Where:** feature/chat/.../RagUi.kt:119-133 (IconButton(..., modifier = Modifier.size(40.dp)) inside a heightIn(min = 40.dp) chip), chip row :101
- **What happens now:** the remove control and its chip are 40 dp tall instead of the app's otherwise consistent 48 dp (all other icon buttons measured 48 dp in the device tree).
- **Why it hurts:** slightly harder to hit and inconsistent with the rest of the app for motor-impaired users (passes WCAG 2.5.8 AA at 24 dp; fails the platform/Material 48 dp guidance and the brief's 48 dp target).

### A11Y-17 — Decorative animations ignore the system "remove animations" setting
- **Severity:** P3   **Confidence:** high   **Effort:** S
- **Where:** core/design/.../Chat.kt:334-348 (InkingMark: infinite rotate), core/design/.../Shell.kt page AnimatedContent (fadeIn + slideInVertically)
- **What happens now:** neither animation checks the system animator duration scale / "remove animations" accessibility setting; the inking mark spins for the whole generation.
- **Why it hurts:** users with vestibular sensitivity or cognitive fatigue asked the OS to reduce motion and the app ignores it (WCAG 2.3.3 is AAA, but honouring the platform preference is expected and a continuously spinning glyph next to streaming text distracts ADHD/dyslexic readers).
- **Fix:** read LocalView's animation scale (or LocalMotionDurationScale) and fall back to a static mark and no slide when it is 0.
- **Verify:** set animator duration scale to 0 / "remove animations": streaming shows a static mark and page changes cross-fade only.

### A11Y-18 — Export result relies on a Toast
- **Severity:** P3   **Confidence:** high   **Effort:** S
- **Where:** feature/chat/.../ChatHistory.kt:98-103 (Toast.makeText(… export_saved / export_failed))
- **What happens now:** success/failure of share/export is a short Toast; on failure it also falls back to the share sheet. Toasts are not associated with the row, are easy to miss and are inconsistently announced by screen readers.
- **Why it hurts:** a blind or distracted user may not learn that the export failed and nothing was written to Downloads.
- **Fix:** show the result inline (a small status line under the row or a snackbar with an action) and announce it via a live region.
- **Verify:** TalkBack: export a conversation; both success and a forced failure are spoken and visible in-app.

### RTL-01 — The composer hard-codes RTL content direction, including in the English UI
- **Severity:** P3   **Confidence:** high   **Effort:** S
- **Where:** core/design/.../Chat.kt:116-119 (textDirection = TextDirection.ContentOrRtl on the composer's text style), while the rest of the field follows LocalLayoutDirection
- **What happens now:** in the English (LTR) UI a neutral or empty draft (numbers, punctuation, emoji) is laid out with an RTL base direction; typed English text is LTR because it has strong LTR characters, but the caret and trailing punctuation can jump when the draft starts with a digit or symbol.
- **Why it hurts:** mixed-direction drafts show the caret and trailing punctuation on the wrong side for English users; Arabic users are unaffected (the default is correct for them).
- **Fix:** use TextDirection.Content (content-derived) or if (LocalLayoutDirection.current == Rtl) ContentOrRtl else ContentOrLtr.
- **Verify:** English UI: type "123" then "٤٥٦" then "hello"; the caret and punctuation must follow the direction of the typed run.

### RTL-02 — Ordered-list markdown markers are not direction-pinned and use a fixed 18 dp gutter
- **Severity:** P3   **Confidence:** medium   **Effort:** S
- **Where:** core/design/.../Markdown.kt:625-640 (marker (block.start + index).toString() + "."; Modifier.widthIn(min = listMarkerWidth)), contrast with the careful TextDirection.Ltr pinning used for code blocks at :575-590
- **What happens now:** the marker is a Latin-digit plus "." run inside an RTL paragraph; at list numbers of 10 or more, or at 130% in-app text scale, the token can exceed the 18 dp gutter and the "." may render on the opposite side of the number.
- **Why it hurts:** numbered answers ("1. 2. 3.") are the most common Arabic answer format in this app; mis-ordered markers or a wrapped gutter degrade readability and trust in technical answers.
- **Fix:** pin the marker TextDirection.Ltr and give the gutter widthIn(min = 18.dp, max = 24.dp), or use a hanging indent with the marker measured.
- **Verify:** an Arabic conversation with a 12-item ordered list at 130% scale: markers render "10." not ".10" and align to the text start.

### RTL-03 — No RTL regressions found in layout primitives (positive finding, recorded to stop re-reporting)
- **Severity:** P3   **Confidence:** high   **Effort:** S
- **Where:** global
- **What happens now:** device evidence confirms correct mirroring: back arrow points right, send arrow left, nav order right-to-left (المحادثة/المكتبة/الإعدادات), active-row accent on the right, end-aligned action icons, RTL ellipsis on the correct side (12-history-ar.png, 10-chat-existing-ar.png); the code uses start/end padding (never absolute*), one conditional offset for the answer actions (Chat.kt:230), four Icons.AutoMirrored uses for the only directional glyphs, and supportsRtl="true" in the manifest.
- **Why it hurts:** nothing — this is the strongest part of the app's i18n and should not be churned during fixes.
- **Fix:** keep start/end and AutoMirrored icons for any new surface; add a screenshot diff at RTL for new rows.
- **Verify:** the listed device nodes/screenshots remain correct after the a11y fixes (which must not change geometry).

### I18N-01 — The model chip clips its own status to a dot at 100% text scale
- **Severity:** P2   **Confidence:** high   **Effort:** S
- **Where:** chat header model chip (core/design/.../Chat.kt:415-436: Row with GirihTick + label maxLines = 1 + " · $status" maxLines = 1, no weights)
- **What happens now:** with an installed model the device tree shows the status TextView measured at only **26 px (13 dp)** wide (10-chat-empty-nodes.txt line 4: text "· جاهز على الجهاز", bounds [256,196][282,229]), so only "·" is visible; the screenshot shows "… qwen2.5 1.5b instruct ·" and the ready state is unreadable. With no model loaded the chip has room and shows "· غير محمّل" fully (13-history-menu).

### I18N-02 — Privacy audit timestamps use locale defaults, breaking the app's "Latin digits only" policy
- **Severity:** P2   **Confidence:** medium   **Effort:** S
- **Where:** feature/privacy/.../PrivacyFormat.kt:49-50 (DateFormat.getDateTimeInstance(SHORT, SHORT) with no locale) used at NetworkAuditSheet.kt:144 and AiReportsSheet.kt:135

### I18N-03 — Arabic metadata at 11 sp with +0.3 sp letter spacing
- **Severity:** P2   **Confidence:** medium   **Effort:** S
- **Where:** core/design/.../Type.kt (labelSmall = style(11, 16, Medium, PlexArabicFamily, letterSpacing = 0.3)); used for the meter (ChatMeter.kt:46, 65), message count (ChatHistory.kt:288), citation page (RagUi.kt:393), badges and pills
- **What happens now:** 11 sp is below the 12 sp floor common for Arabic UI text, and positive letter spacing on a connected Arabic script fights the cursive joins (tracking is applied after shaping, visibly separating letters that should join).
- **Why it hurts:** Arabic glyphs carry most of their identity in baseline joins and dots; at 11 sp with tracking, "2 رسالة" / "رمز تقديري" and citation pages are the hardest strings in the UI to read — precisely the metadata a user needs when checking state and trust.
- **Fix:** set labelSmall to 12 sp / 18 with letterSpacing = 0 for Arabic (the family is Arabic-first; Latin at 12/0 is unproblematic).
- **Verify:** screenshot the meter and citation row at default scale and compare legibility; no layout row may grow (labelSmall is inline metadata).

### I18N-05 — No android:localeConfig, so the OS per-app language list cannot show Arabic/English

### I18N-07 — Percentage strings use ASCII "%" directly after a Latin number inside Arabic sentences
- **Severity:** P3   **Confidence:** medium   **Effort:** S

### FS-01 — Text scale multiplies the system font scale with no cap, while text boxes are fixed-height
- **Severity:** P1   **Confidence:** high   **Effort:** M
- **Where:** core/design/.../FontScale.kt (applyTo(platformFontScale) = platformFontScale * factor; ids 85/100/115/130; ProvideFontScale overrides LocalDensity.fontScale only), applied at app/.../SirrakApp.kt:52; interacting with fixed text boxes: composer heightIn(max = 160.dp) plus maxLines = 6 (Chat.kt:112-125), model chip maxLines = 1 twice (Chat.kt:425, 433), settings values maxLines = 1 (Settings.kt:104), pills maxLines = 1 (Page.kt:109), citations maxLines = 1 (RagUi.kt:388)
- **What happens now:** the in-app "أكبر" preset multiplies the user's system font scale. With Android's 200% accessibility setting the effective scale is 2.6x (1.3 x 2.0); every sp grows, but the composer is capped at 160 dp (about 2 lines at that scale), the model chip and status pills stay single-line and ellipsise, and the composer field (312 px / 2 = 156 dp wide, measured in 10-chat-empty.xml) drops to roughly 10 Arabic characters per line.
- **Why it hurts:** the user who most needs large text gets a composer where they cannot see what they type and a status chip that says nothing — the feature meant to help creates a worse state than the default.
- **Fix:** cap the effective scale (for example min(platform * factor, 2.0)) or make the in-app presets replace the system factor when the system is at accessibility sizes; raise the composer max height and let the chip wrap to two lines at large scales; add a device test at 1.3 x system 2.0.
- **Verify:** set system font 200% plus in-app "أكبر": type a two-line message and read the header chip; both must remain usable, with a screenshot as acceptance evidence.

### FS-02 — Single-line metadata has no truncation strategy at large scales
